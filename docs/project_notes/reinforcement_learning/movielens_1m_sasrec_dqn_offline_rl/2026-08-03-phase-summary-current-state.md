# 2026-08-03 阶段总结与当前状态

## 本阶段在做什么

这一阶段的核心目标不是直接发明新算法，而是把 `movielens_1m_sasrec_dqn_offline_rl` 从一个“能跑但不稳、能出数但不可信”的原型，推进成一个：

- 有明确上游复用来源
- 有稳定训练闭环
- 有可解释评估口径
- 有当前最优主线候选

的离线序列推荐强化学习项目。

更直白地说，这一阶段完成的是：

- 把系统救活
- 把评估修正
- 把主线跑稳
- 把最强 baseline 打磨出来

## 已完成的主线演进

截至 2026-08-03，这个项目的演进大致经历了下面几个阶段。

### 1. 项目骨架与上游复用完成

我们已经完成：

- 复用上游 `movielens_1m_sasrec_baseline`
- 构建离线 replay buffer
- 复用 `SASRec encoder`
- 接上 `Q-head`
- 实现 `Double DQN + CQL` 训练循环
- 实现 `test / all` 两套离线评估脚本

这一步解决的是“有没有完整工程闭环”的问题。

### 2. 早期失败暴露出两个核心问题

最早的几轮实验很快暴露出两类典型问题：

- Q-value 抬升过快，出现明显 value explosion 倾向
- `valid_total_loss` 改善，但 `HR@10 / NDCG@10` 并不随之改善

这让我们明确认识到：

- 离线 RL 的数值稳定性是第一道门槛
- 训练 loss 不能直接当成推荐效果代理

### 3. 稳定化修正落地

随后我们引入了多轮稳定化修正：

- `soft target update`
- `Huber TD loss`
- 降低 `gamma`
- reward 改成 binary
- 监控 `TD / CQL` 相对强度
- `valid ranking metric` 进入选模环节

这一步的价值不是直接提分，而是把训练从“动不动发散”拉回到“可以认真比较实验”的区间。

### 4. 选模逻辑从 loss 切到 ranking

这个阶段最关键的工程修正之一是：

- 不再按 `valid_total_loss` 选 best checkpoint
- 改为按 `valid_ndcg_at_10` 选模

这一步非常重要，因为它把：

- “训练目标”

和

- “推荐排序目标”

区分开了。

从这个阶段开始，实验结果才真正变得可解释。

### 5. gamma 回调把过度保守拉回合理区间

我们已经验证过：

- `gamma = 0.7` 太短视，排序能力掉得太厉害
- `gamma = 0.85` 明显恢复
- `gamma = 0.9` 进一步把 `test/all NDCG` 与整体轨迹表现往上推

所以当前主线已经不再停留在“单纯稳住”，而是进入了：

- 在稳定前提下恢复排序质量

的阶段。

### 6. CE regularization 把“排序感”重新加回来

这是当前阶段最重要的训练目标升级。

我们把损失从：

- `TD + CQL`

扩展成：

- `RL loss + CE regularization`

它的物理意义是：

- RL 负责长期价值
- CE 负责维持尖锐的 next-item 排序边界

这一步非常关键，因为它第一次明确证明：

- 当前这个项目里，离线 RL 和监督排序不是冲突关系
- 相反，它们是互补关系

## 当前主线最优候选

截至 2026-08-03，当前最强主线候选是：

- `cql_huber_gamma09_binary_reward_valid_ndcg_ce_reg05`

它对应的训练与评估结果表明：

- `best_valid_ndcg_at_10` 目前最高
- `test HR@10` 目前最高
- `test NDCG@10` 目前最高
- 训练不再只在 `epoch 1` 才能达到最好，说明训练目标比之前更健康

关键结果如下：

- `test HR@10 = 0.19039735099337748`
- `test NDCG@10 = 0.1021792974824788`
- `all HR@10 = 0.24074176523307406`
- `all NDCG@10 = 0.12533210207531637`

这说明当前项目已经从“离线 RL 会不会把推荐系统练坏”走到了：

- “我们已经有一条可用而且还在持续变强的主线”

## 但为什么现在还不能说项目已经做完

虽然当前结果已经明显比最初版本强很多，但这个项目还没有到“终局”。

当前仍然有三个未彻底解决的问题。

### 1. 训练目标仍然偏经验主义

我们现在的主线确实有效，但还属于：

- `CQL-style DQN + supervised ranking regularization`

这更像一个很强的工程基线，还不是明确的“算法创新终版”。

### 2. 当前最强点仍是单条参数路线的结果

虽然 `ce=0.5` 已经暂时最好，但我们还没有完成：

- `0.3 ~ 0.5` 之间的完全收口
- 多 seed 稳定性验证
- 更严格的泛化比较

也就是说，当前 best candidate 很强，但还需要收敛确认。

### 3. 更高层次的创新还没正式展开

目前这个阶段主要还是：

- 让现有 DQN/CQL 主线稳定并提强

但真正更上层的创新点，比如：

- behavior-constrained offline RL
- 更好的 ranking-aware objective
- 更合理的 candidate / negative 设计

都还没有正式进入实现阶段。

## 本阶段最重要的认识

这一阶段最有价值的不是某一个单点分数，而是沉淀出了几条非常关键的项目认识。

### 1. 离线 RL 推荐里，训练稳定性先于“花哨结构”

如果 Q-value 失控、选模口径混乱，那么再复杂的结构也只是在噪声上叠噪声。

### 2. 不能把训练 loss 当成推荐目标代理

当前项目已经清楚表明：

- `valid_total_loss` 好看

并不等于

- `valid/test NDCG@10` 更好

### 3. RL 与监督排序需要结合，而不是二选一

在当前问题上：

- 纯 RL 容易丢掉排序感
- 纯监督又没有长期价值建模

所以联合损失不是折中，而是必要组合。

### 4. 参数调优不是终局，但它是后续创新的地基

这个阶段看起来调了很多参数，但本质上是在完成一件基础工作：

- 建一个可信的 strongest baseline

没有这个地基，后面谈方法创新往往只是碰运气。

## 当前状态总结

截至 2026-08-03，这个项目当前最准确的定位是：

- 工程闭环已成熟
- 训练与评估口径已稳定
- 主线候选已形成
- baseline 已具备继续向方法创新推进的基础

所以，项目现在已经不再是：

- “能不能做出来”

而是：

- “在当前最强主线之上，下一步该往哪里创新”

这意味着项目已经从“救火式原型阶段”，正式进入：

- 基线收口 + 方法升级路线规划阶段
